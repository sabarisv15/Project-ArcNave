## What ARCNAVE Is

A multi-tenant college ERP (Node.js/Express, plain JS, PostgreSQL + pgvector) with an AI copilot. Architecture: `Auth/RBAC/Tenant → AI Orchestration (aiService.js) → Tool Registry (aiToolRegistry.js) → Policy Gate → Business Services → arcnave_app (least-privilege DB role) → PostgreSQL RLS`. ~62 registered AI tools, each a thin wrapper over one Business Service method — never raw SQL, never direct repository access from AI code. This is not a general chatbot; the product principle is **GUI-parity**: anything a role can legitimately do through the GUI should be operable through natural language, subject to the same RBAC/approval rules.

**Real deviations from the original design, worth knowing before touching this code again:**
- **P0.6 was not in the original roadmap at all.** Mid-P0, discovered the frontend chat (`WorkspaceProvider.jsx`) was 100% mocked (`generateReply()`+`setTimeout`, no `api/ai.js` existed) — none of P0's backend work would have been reachable by a real user. Flagged to the user, approved, built as part of P0 (new `api/ai.js`, real `/ai/ask/stream` wiring, `runAiTurn` detached from `sendMessage` so navigation isn't blocked on the full AI response).
- **P0.2 (tool-schema filtering) was partially already done.** `aiToolRegistry.listTools({ role })` already filtered by role — the real remaining gap was a broad role (principal) still keeping ~56/57 tools. Added `filterToolsByRelevance` (keyword-overlap ranking, hard-capped at 25, never excludes a tool with any overlap) on top of the existing role filter.
- **P0.4 (evidence/provenance) and the "verification" half of Bucket B merged into one mechanism**, per the correction already recorded in the (now-historical) roadmap section below — implemented as `buildEvidence`/`buildEvidenceTrail`/`verifyNumericClaims` in `aiService.js`.
- **A double-DB-query bug was caught and fixed while building P0.3**: `executeWorkflowPlan` was recomputing `aiActorContext.describeIdentityContext` independently instead of reusing the caller's already-computed value, worth an extra `collegeProfileService.getProfile` call on every plan execution — fixed by threading `identityBlock`/`adapter`/`aiConfig` through from `askAgent`.
- **A regression was caught by the existing `db-role-timeouts.test.js`-style discipline during P1.3**: not a repeat of the earlier pool-level `statement_timeout` bug, but the same *kind* of thing — none this time, model routing landed clean, mentioned here only because the pattern (real DB-level tests catching a real conflict) held again.
- **P2.3 (Trusted Web Retrieval) is retrieval, not search.** No search API is configured anywhere in this codebase — the shipped tool (`fetch_trusted_web_page`) takes a specific, already-known `https://` URL and validates it against a domain allowlist (SSRF-hardened: no IP literals, no embedded credentials, no redirects followed, https-only), it does not accept an open-ended query. A real search capability would need a configured search provider first.
- **P2.4 (scoped preference memory) reused existing infrastructure instead of building a new table.** `userPreferenceService`/the `user_preferences` table already existed, already RLS-scoped per `(college_id, user_id)`, already had `user_preferences_list`/`user_preferences_set` AI tools — but the existing `user_preferences_set` tool had **no key restriction at all** ("use whatever key name," by design, for a future human-driven settings UI that doesn't exist yet). Restricted the **AI tool's handler** (not the underlying service, which stays general-purpose for that future UI) to an explicit allowlist (`report_format`, `default_chart`, `language`) — real enforcement in the handler, not just a JSON-schema `enum` hint, since `assertParamsValid` doesn't check `enum`.

## Historical: Next Flagged Phase — AI Capability Roadmap (queued, not started)

Flagged 2026-08-20 across several rounds of comparison (Claude Code's own capabilities vs. ARCNAVE's AI copilot), refined once by the user into a P0/P1/P2 roadmap, then cross-checked against real code/schema before being locked in here (not taken at face value — 2 feasibility claims verified, 3 design corrections made; see below). Explicitly deferred until the current round of discussion is done — this is the scope for **one future implementation pass**, prioritized, not a flat list.

**Root cause, one sentence:** `askAgent`/`askAboutTool` are fully stateless (`aiService.js:126-128`'s own comment — "Every /ai/ask call remains fully independent... takes no history parameter") and invoke at most one tool per request — every item below either fixes that directly or builds on top of the fix.

**Governing framing (the user's own, worth preserving):** without follow-up capability, the `/ai/ask` chat page is a chat *shell* over a stateless Q&A tool, not a real chatbot. This is the concrete product cost of round 3's decision to reject persistent memory — a deliberate security trade-off for a multi-tenant ERP, not an oversight — but round 3 itself already recommended the narrow fixes below, not "leave it stateless forever." Every item stays bounded/scoped on purpose; none of this is "copy what Claude does" wholesale.

**Corrections made while locking this in (verified against real code before accepting):**
1. **Evidence/provenance and "LLM self-verification" are one mechanism, not two.** Both need "re-query the DB/tool and compare against the LLM's claim" — provenance is that re-query exposed as a human-readable trail ("based on: attendance records, 1,248 rows, updated 20 Aug"), verification is the same re-query exposed as a PASS/CONFLICT/INSUFFICIENT_EVIDENCE gate. Merged into one item (P0 #5 below) so there's one re-query path, not two.
2. **The Bounded Workflow Engine's Policy Gate is already per-step in the real code, not a single upfront checkpoint.** Verified: `aiToolRegistry.js`'s Policy Gate runs *inside* `invokeTool`, so as long as the executor calls the existing `invokeTool` per plan step (reuse, don't reinvent), the gate automatically re-fires per step. Written that way below, not as one gate before Step 1.
3. **"Sub-agents" is implemented as plain concurrent `Promise.all`, never a worker/agent framework.** 2-4 independent read-only tool calls inside the same request/transaction/actor-identity — a concurrency helper, not a queue/pool abstraction (avoids the god-service over-engineering risk round 2 already flagged once this session for a different item).
4. **Schema feasibility confirmed:** `audit_log.metadata` is plain `JSONB` (migration `1751500000000`) — token/cost telemetry and evidence/provenance fields are purely additive, no migration needed for either.

### P0 — foundational, unlocks everything else

1. **Short-session conversation memory** (round 3) — NOT persisted across sessions/cross-tenant, scoped to the current `conversationService.js` conversation only. `askAgent`/`askAboutTool` need a history parameter, threaded into the prompt.
2. **Bounded multi-step workflow engine** (round 6/7, corrected above) — plan once (ordered tool calls, hard step cap ~5-6, max execution time, allowed tools fixed before execution, no recursive plan creation) → executor calls the existing `invokeTool` per step (Policy Gate re-fires automatically, per correction #2) → one synthesis call → plan-level confirmation for any write (reuses the existing L3 confirmation-pause UX, no new mechanism).
3. **Streaming** — no SSE/`EventSource` anywhere in `api/client.js` or the 4 provider adapters today; user stares at a blank screen for the full 20-30s+ generation. Matters most exactly where the workflow engine makes answers longer (multi-step reports) — build together. Gemini/Claude both support SSE; needs a streaming route + token-by-token render in `ChatMessage.jsx`. Ideal shape: stream plan/tool-execution status, then the final synthesis.
4. **Tool-schema filtering** — ~11k tokens of all ~63 tool schemas sent on every call today, no filtering. Filter by `actor → role → tenant → module → operation → current task`. Natural to build alongside #2 since the workflow engine already touches tool-selection logic.
5. **Evidence/provenance + verification** (merged per correction #1) — `LLM claim → evidence extraction → deterministic DB/tool re-query → compare → PASS/CONFLICT/INSUFFICIENT_EVIDENCE`. Gate output gets used two ways: (a) blocks/flags a write if CONFLICT, next to the existing deterministic diff-check from round 2, never replacing it; (b) surfaces as a human-readable "based on: source → tool → query/result → timestamp" trail, never raw SQL. This is ARCNAVE's real structural advantage over a generic Claude-style chatbot (round 3: "authoritative ground truth... can verify its own model's claims cheaply") — worth building as core, not polish.

### P1 — high value once P0 lands, or cheap enough to batch together

6. **Token/cost telemetry** — Gemini's own `usageMetadata` (`promptTokenCount`/`candidatesTokenCount`) is already returned and currently discarded in `gemini.js`; likely true for the other 3 adapters' usage fields too. Log input/output/cached tokens, model, estimated cost, request/tool latency into the existing `ai_tool_invoked`/`ai_ask` audit metadata (additive JSONB, no migration — correction #4). User-facing usage display is a separate, later concern from internal billing.
7. **Prompt caching** — ARCNAVE repeatedly sends a stable system/product/tenant context; only genuinely applies to Claude in the current adapter set (Gemini's caching API is structurally different, NIM/self-hosted have none) — designed in round 2, still unbuilt.
8. **Model routing** — small/cheap model for classification/simple retrieval, stronger model for reasoning/report generation; deterministic code (never a model) stays authoritative for authorization/critical decisions.
9. **Voice input** — `AIComposer.jsx:240`'s `Mic` icon has no `onClick` at all, purely decorative. A dead affordance is worse than no button — either wire it to the Web Speech API or remove it.
10. **Drag-and-drop attachments** — no `onDrag`/`onDrop` in `AIComposer.jsx` today, file picker/paste only. Natural companion to the existing attachment flow.

### P2 — real gaps, lower urgency or needs more product evidence first

11. **LaTeX/Mermaid rendering** — nothing in `Markdown.jsx` for math or diagrams today. Mermaid must stay **render-only, never executable**. Don't build speculatively — wait for a real assessment-formula/workflow-diagram use case (matches round 6's own no-speculative-building principle).
12. **Code syntax highlighting** — `Markdown.jsx`'s `CodeBlock` renders real `<pre><code>` with no tokenizing. Shiki over Prism (no runtime `eval`).
13. **Trusted Web Retrieval** (safe version of "web search") — `User request → Policy Gate → allowed-domain resolver → web retrieval tool → sanitization → LLM context`, results wrapped in the same `===UNTRUSTED_TOOL_DATA_START/END===` boundary every tool result already gets, explicitly labeled "External/Untrusted." Start allowlist: UGC/AICTE/university/exam-board domains, opt-in per college. **Hard rule: web content can inform an answer, it can never authorize an ARCNAVE action** — a malicious page saying "delete this student" is just text to the untrusted-data boundary, same as any other tool result.
14. **Scoped Preference Memory** (safe version of "persistent memory") — `tenant_id + user_id + memory_type` under RLS, storing only **explicit, structured preference fields** the user opts into (e.g. `report_format`, `default_chart`, `language`). Never freeform inferred facts about students/staff — that would be an unbounded, unauditable PII retention risk.
15. **Parallel Read Workers** (safe version of "sub-agents", per correction #3) — `Promise.all` over 2-4 independent read-only steps within one bounded plan (e.g. attendance + marks + failures + department comparison, fanned out then merged into one report), same tenant/actor/permission boundary as the parent request, no recursive spawning. A concurrency helper inside the existing executor, not a new framework.

### Excluded — arbitrary code execution, not reconsidering without a concrete product requirement

GUI-parity already covers every legitimate action through Business Services; arbitrary Python/JS/shell execution is a large new attack surface for no proportional product value. If a real computational need shows up, expose deterministic tools (`calculate_statistics`, `generate_chart`, `compare_marks`, `calculate_attendance`, `generate_report`) — never `run_any_code()`.

### Round 11 — the 7 P0/P1 fixes from the final pre-launch audit

1. **Login/OTP rate limiting** (P0) — `express-rate-limit`+`helmet` were already `package.json` dependencies but wired into nothing; now applied to `/auth/login` (tenant + platform), MFA verify/resend, password-reset, and both OTP-request routes. Keyed on IP + a SHA-256 hash of the submitted identifier (never the raw username/email) via `middleware/rateLimit.js`. The 50-per-15-min limit on login is measured against this repo's own test-suite volume (`classes.test.js` alone re-authenticates one seeded user 30 times in a single file), not guessed.
2. **Workflow approval TOCTOU race** — `workflowRepository.updatePendingStatus` (conditional `UPDATE ... WHERE status = 'Pending'`, the row lock itself is the concurrency guard) plus reordering `approveRequest`/`rejectRequest`/`escalateRequest` so the guarded update runs *before* `recordAction`/the audit log — a race loser now gets zero side effects, not just a bad state transition. Proven with a real two-connection concurrent test (deterministically forced via a controlled stale-read, since a naive `Promise.all` version was empirically shown to pass even against the unfixed code on a fast local Postgres).
3. **Background-job enqueue race** — `db/tenantTransaction.js` gained `registerAfterCommit`/an `AFTER_COMMIT_CALLBACKS` queue (Symbol-keyed on the request's AsyncLocalStorage context, kept out of the generic per-request log payload on purpose); `backgroundJobService.enqueue`'s worker trigger now fires only after the enqueuing transaction actually commits, never before.
4. **DB-level timeouts** — `ALTER ROLE arcnave_app SET lock_timeout='10s', statement_timeout='20s', idle_in_transaction_session_timeout='90s'` (migration `1762100000000`). Each value reasoned from real code shapes (generateTimetable's bounded statement loop; the 30s LLM adapter timeout and 60s OCR exec timeout the idle setting has to sit above), not a blind default.
5. **AI tool-invoke idempotency** — new `idempotency_keys` table (migration `1762200000000`, deliberately no status column — see its own comment for why atomicity makes one unnecessary) + `idempotencyKeyRepository.js` + `aiService.invokeToolIdempotent`, opt-in via an `Idempotency-Key` header on `POST /ai/tools/:name/invoke`. Reservation, business write, and completion all run on the same per-request transaction so a mid-request crash is safe either way (nothing committed, or the real response is already stored for replay). Caught and fixed a real bug during implementation: the reservation's unique-violation catch needed a `SAVEPOINT`/`ROLLBACK TO SAVEPOINT`, not a bare try/catch — Postgres aborts the whole transaction on any statement error, which broke the subsequent lookup.
6. **Security headers + CORS** — `helmet()` on both `tenantApp.js`/`platformApp.js`; `cors` (new dependency) scoped to one explicit `config.frontendOrigin` (default `http://localhost:3100`, the frontend's real dev port), never a wildcard — verified live via curl, not just unit tests.
7. **PDF/OCR pipeline protection** — fixed the accidental effective ~100KB upload cap (`express.json()`'s `req._body` short-circuit meant the route-level 15mb limit on `/documents/*` never actually applied; now a path-scoped parser ahead of the app-wide default); added a 60s exec timeout and a 250-page safety ceiling to `pdftoppm` (the page number is real evidence, not a guess — measured against the actual poppler build via `docker run gstack-app:latest`, a busy A4 page rasterized to ~650KB at 200 DPI; explicitly a technical safety net, not a product decision on real document size limits); added `ocr/ocrConcurrencyLimit.js`, a 2-slot in-process semaphore shared by both real OCR entry points (`documentExtractionService.runOcr` and `documentSearchService.js`'s ingestion, which previously had no shared choke point at all).

## Governing Principles Established This Session (apply these without re-deriving them)

- **Minimum sufficient work, scoped per-operation, not per-request.** A single-fact query may skip the LLM; a genuine multi-step request still needs planning + synthesis calls — never conflate the two.
- **"Less unnecessary work," not "less LLM calls."** A 4-tool workflow needing 2 reasoning calls (plan once, synthesize once) is correct; forcing it to 1 call or letting it balloon to 5+ are both wrong.
- **Verification is deterministic code, never a second LLM call.** Diff the LLM's numeric claim against the value already computed; correct in place.
- **GUI parity is bounded by Business Service coverage, not by what SQL could technically do.** There is no tool for "DROP TABLE" because there's no GUI button for it either — this is why AI can be capable without being an admin.
- **Interface/schema decisions get front-loaded pre-launch** (async contracts, worker abstractions, cache-hint slots); **usage-volume-gated infra decisions do not** (Redis, GPU, dedicated workers) — launch status doesn't change the latter.
