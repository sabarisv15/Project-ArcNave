## What ARCNAVE Is

A multi-tenant college ERP (Node.js/Express, plain JS, PostgreSQL + pgvector) with an AI copilot. Architecture: `Auth/RBAC/Tenant → AI Orchestration (aiService.js) → Tool Registry (aiToolRegistry.js) → Policy Gate → Business Services → arcnave_app (least-privilege DB role) → PostgreSQL RLS`. ~62 registered AI tools, each a thin wrapper over one Business Service method — never raw SQL, never direct repository access from AI code. This is not a general chatbot; the product principle is **GUI-parity**: anything a role can legitimately do through the GUI should be operable through natural language, subject to the same RBAC/approval rules.

## Session Arc (9 rounds — analysis first, implementation last)

1. **Current AI architecture audit** — mapped the real pipeline (not assumed): `aiService.js` → `aiToolRegistry.js` (Policy Gate, L1/L2/L3 authority levels) → `aiContextBuilder.js`/`aiPromptSafetyLayer.js` (untrusted-data boundary) → 4 provider adapters (`claude.js`/`gemini.js`/`nim.js`/`selfHosted.js`, production default = self-hosted NIM Llama-3.1-8B, **not** Claude). Found: no prompt caching, no tool-schema filtering (full ~63-tool list sent every call), no output bounds on 3/4 adapters, blanket unconditional OCR (no native-text-first triage), a genuinely well-designed security substrate (Policy Gate + RLS + audit log) already in place.
2. **Cost optimization review** — validated/refined: tool retrieval (deterministic domain-prefix first, embeddings deferred until real usage data exists), role-level prompt caching, deterministic pre-aggregation for large tool results, deterministic verification (diff LLM numeric claims against already-computed values, never a second LLM call).
3. **Latency review (internal compute vs. LLM)** — the real risk is *un-parallelized* deterministic work (sequential OCR can exceed LLM-only latency), not determinism itself. Fix is parallelization + async-by-default document processing, not fewer deterministic steps. Rule: perceived latency (is the user blocked?) matters, not total compute time.
4. **Investment/TCO review** — staged infra (1 college / 5 colleges / 50 colleges), real researched pricing (DigitalOcean, Hetzner, AWS, GPU rental, Claude/Gemini). GPU not needed at any modeled stage. Redis/dedicated workers deferred until real multi-tenant document concurrency exists, not built pre-emptively.
5. **Pre-launch reassessment** — since ARCNAVE has zero production users, front-loaded schema/interface decisions that are cheap now and expensive after real tenant data exists (async document API contract, worker/queue abstraction, provider cache-hint interface), while still deferring anything gated by usage volume (Redis, GPU, embeddings-based retrieval) regardless of launch status.
6. **GUI-parity / agentic workflow review** — validated the core product principle (AI should reach any GUI-equivalent action via the same Business Services, never a parallel path). Designed a *bounded* multi-step workflow engine (plan once → deterministic tool execution → one synthesis call, hard step cap, plan-level confirmation for any write) — explicitly rejected unbounded/autonomous agentic loops.
7. **Database-destruction security audit** — verified (not assumed) with real evidence: RLS is enabled on 62+ tables with `FORCE ROW LEVEL SECURITY`; `arcnave_app` is a non-superuser role with per-table least-privilege grants; `audit_log` has `SELECT, INSERT` only (no UPDATE/DELETE — append-only at the DB layer, not just convention); `colleges` has `SELECT` only for the runtime role (a college/tenant cannot be deleted even by a fully compromised app layer); migrations run under a separate, never-app-used credential. One real gap found: `students` table's DELETE grant is broader than any code path uses (flagged, not yet narrowed). No bulk-operation row-count ceiling existed at the time (closed in round 9).

## Historical: Next Flagged Phase — AI Capability Roadmap (queued, not started)

Flagged 2026-08-20 across several rounds of comparison (Claude Code's own capabilities vs. ARCNAVE's AI copilot), refined once by the user into a P0/P1/P2 roadmap, then cross-checked against real code/schema before being locked in here (not taken at face value — 2 feasibility claims verified, 3 design corrections made; see below). **Corrections made while locking this in (verified against real code before accepting):**
1. **Evidence/provenance and "LLM self-verification" are one mechanism, not two.** Both need "re-query the DB/tool and compare against the LLM's claim" — provenance is that re-query exposed as a human-readable trail ("based on: attendance records, 1,248 rows, updated 20 Aug"), verification is the same re-query exposed as a PASS/CONFLICT/INSUFFICIENT_EVIDENCE gate. 2. **The Bounded Workflow Engine's Policy Gate is already per-step in the real code, not a single upfront checkpoint.** Verified: `aiToolRegistry.js`'s Policy Gate runs *inside* `invokeTool`, so as long as the executor calls the existing `invokeTool` per plan step (reuse, don't reinvent), the gate automatically re-fires per step. 3. **"Sub-agents" is implemented as plain concurrent `Promise.all`, never a worker/agent framework.** 2-4 independent read-only tool calls inside the same request/transaction/actor-identity — a concurrency helper, not a queue/pool abstraction (avoids the god-service over-engineering risk round 2 already flagged once this session for a different item).
4. **Schema feasibility confirmed:** `audit_log.metadata` is plain `JSONB` (migration `1751500000000`) — token/cost telemetry and evidence/provenance fields are purely additive, no migration needed for either.

### P0 — foundational, unlocks everything else

1. **Short-session conversation memory** (round 3) — NOT persisted across sessions/cross-tenant, scoped to the current `conversationService.js` conversation only. `askAgent`/`askAboutTool` need a history parameter, threaded into the prompt.
2. **Bounded multi-step workflow engine** (round 6/7, corrected above) — plan once (ordered tool calls, hard step cap ~5-6, max execution time, allowed tools fixed before execution, no recursive plan creation) → executor calls the existing `invokeTool` per step (Policy Gate re-fires automatically, per correction #2) → one synthesis call → plan-level confirmation for any write (reuses the existing L3 confirmation-pause UX, no new mechanism).
3. **Streaming** — no SSE/`EventSource` anywhere in `api/client.js` or the 4 provider adapters today; user stares at a blank screen for the full 20-30s+ generation. Matters most exactly where the workflow engine makes answers longer (multi-step reports) — build together. Gemini/Claude both support SSE; needs a streaming route + token-by-token render in `ChatMessage.jsx`. Ideal shape: stream plan/tool-execution status, then the final synthesis.
4. **Tool-schema filtering** — ~11k tokens of all ~63 tool schemas sent on every call today, no filtering. Filter by `actor → role → tenant → module → operation → current task`. Natural to build alongside #2 since the workflow engine already touches tool-selection logic.
5. **Evidence/provenance + verification** (merged per correction #1) — `LLM claim → evidence extraction → deterministic DB/tool re-query → compare → PASS/CONFLICT/INSUFFICIENT_EVIDENCE`. This is ARCNAVE's real structural advantage over a generic Claude-style chatbot (round 3: "authoritative ground truth... can verify its own model's claims cheaply") — worth building as core, not polish.

GUI-parity already covers every legitimate action through Business Services; arbitrary Python/JS/shell execution is a large new attack surface for no proportional product value. Caught only once a real Gemini key was wired in and a live `/ai/ask` call was made — this adapter was previously never live-verified (its own header comment already flagged that).

Each value reasoned from real code shapes (generateTimetable's bounded statement loop; the 30s LLM adapter timeout and 60s OCR exec timeout the idle setting has to sit above), not a blind default.
5. **AI tool-invoke idempotency** — new `idempotency_keys` table (migration `1762200000000`, deliberately no status column — see its own comment for why atomicity makes one unnecessary) + `idempotencyKeyRepository.js` + `aiService.invokeToolIdempotent`, opt-in via an `Idempotency-Key` header on `POST /ai/tools/:name/invoke`. ## Governing Principles Established This Session (apply these without re-deriving them)

- **Minimum sufficient work, scoped per-operation, not per-request.** A single-fact query may skip the LLM; a genuine multi-step request still needs planning + synthesis calls — never conflate the two.
- **"Less unnecessary work," not "less LLM calls."** A 4-tool workflow needing 2 reasoning calls (plan once, synthesize once) is correct; forcing it to 1 call or letting it balloon to 5+ are both wrong.
- **Verification is deterministic code, never a second LLM call.** Diff the LLM's numeric claim against the value already computed; correct in place.
- **GUI parity is bounded by Business Service coverage, not by what SQL could technically do.** There is no tool for "DROP TABLE" because there's no GUI button for it either — this is why AI can be capable without being an admin.
- **Interface/schema decisions get front-loaded pre-launch** (async contracts, worker abstractions, cache-hint slots); **usage-volume-gated infra decisions do not** (Redis, GPU, dedicated workers) — launch status doesn't change the latter.
