## What ARCNAVE Is

A multi-tenant college ERP (Node.js/Express, plain JS, PostgreSQL + pgvector) with an AI copilot. Architecture: `Auth/RBAC/Tenant → AI Orchestration (aiService.js) → Tool Registry (aiToolRegistry.js) → Policy Gate → Business Services → arcnave_app (least-privilege DB role) → PostgreSQL RLS`. ~62 registered AI tools, each a thin wrapper over one Business Service method — never raw SQL, never direct repository access from AI code. This is not a general chatbot; the product principle is **GUI-parity**: anything a role can legitimately do through the GUI should be operable through natural language, subject to the same RBAC/approval rules.

## Session Arc (9 rounds — analysis first, implementation last)

1. **Current AI architecture audit** — mapped the real pipeline (not assumed): `aiService.js` → `aiToolRegistry.js` (Policy Gate, L1/L2/L3 authority levels) → `aiContextBuilder.js`/`aiPromptSafetyLayer.js` (untrusted-data boundary) → 4 provider adapters (`claude.js`/`gemini.js`/`nim.js`/`selfHosted.js`, production default = self-hosted NIM Llama-3.1-8B, **not** Claude). Found: no prompt caching, no tool-schema filtering (full ~63-tool list sent every call), no output bounds on 3/4 adapters, blanket unconditional OCR (no native-text-first triage), a genuinely well-designed security substrate (Policy Gate + RLS + audit log) already in place.
2. **Cost optimization review** — validated/refined: tool retrieval (deterministic domain-prefix first, embeddings deferred until real usage data exists), role-level prompt caching, deterministic pre-aggregation for large tool results, deterministic verification (diff LLM numeric claims against already-computed values, never a second LLM call).
3. **Latency review (internal compute vs. LLM)** — the real risk is *un-parallelized* deterministic work (sequential OCR can exceed LLM-only latency), not determinism itself. Fix is parallelization + async-by-default document processing, not fewer deterministic steps. Rule: perceived latency (is the user blocked?) matters, not total compute time.
4. **Investment/TCO review** — staged infra (1 college / 5 colleges / 50 colleges), real researched pricing (DigitalOcean, Hetzner, AWS, GPU rental, Claude/Gemini). GPU not needed at any modeled stage. Redis/dedicated workers deferred until real multi-tenant document concurrency exists, not built pre-emptively.
5. **Pre-launch reassessment** — since ARCNAVE has zero production users, front-loaded schema/interface decisions that are cheap now and expensive after real tenant data exists (async document API contract, worker/queue abstraction, provider cache-hint interface), while still deferring anything gated by usage volume (Redis, GPU, embeddings-based retrieval) regardless of launch status.
6. **GUI-parity / agentic workflow review** — validated the core product principle (AI should reach any GUI-equivalent action via the same Business Services, never a parallel path). Designed a *bounded* multi-step workflow engine (plan once → deterministic tool execution → one synthesis call, hard step cap, plan-level confirmation for any write) — explicitly rejected unbounded/autonomous agentic loops.
7. **Database-destruction security audit** — verified (not assumed) with real evidence: RLS is enabled on 62+ tables with `FORCE ROW LEVEL SECURITY`; `arcnave_app` is a non-superuser role with per-table least-privilege grants; `audit_log` has `SELECT, INSERT` only (no UPDATE/DELETE — append-only at the DB layer, not just convention); `colleges` has `SELECT` only for the runtime role (a college/tenant cannot be deleted even by a fully compromised app layer); migrations run under a separate, never-app-used credential. One real gap found: `students` table's DELETE grant is broader than any code path uses (flagged, not yet narrowed). No bulk-operation row-count ceiling existed at the time (closed in round 9).
8. **First backend optimization pass** — dead code removal, transaction-rollback bug fix, N+1 fixes, output-token bounds, missing indexes. See `CHANGES.md` for exact diff.
9. **Second backend optimization pass** — the 6 findings explicitly deferred from round 8, now closed. See `CHANGES.md` for exact diff.
10. **Final pre-launch proof audit** — 6 parallel investigation agents, one per area (concurrency/transactions/DB resources; AI workflow safety/prompt injection; database integrity/migrations; document pipeline/uploads; provider safety/secrets/API hardening; auditability/test quality/dead code). Verdict: **READY AFTER SPECIFIC FIXES**, not NOT READY (the core security substrate — RLS, Policy Gate, tenant isolation, audit-log immutability, AI/SQL/filesystem boundary — held up under every adversarial scenario tested) and not PRE-LAUNCH READY (one real P0 — no login rate limiting — plus a coherent P1 cluster). ## What's Actually Implemented in Code (not just recommended)

Three real implementation passes have now landed, fully tested (**1,759/1,759 tests passing** against a real local Postgres as of this checkpoint — 1,732 from the two optimization passes + 27 new tests from the round-11 fix pass). Full file-by-file diff for all three: see `CHANGES.md`.

### Round 11 — the 7 P0/P1 fixes from the final pre-launch audit

1. **Login/OTP rate limiting** (P0) — `express-rate-limit`+`helmet` were already `package.json` dependencies but wired into nothing; now applied to `/auth/login` (tenant + platform), MFA verify/resend, password-reset, and both OTP-request routes. Keyed on IP + a SHA-256 hash of the submitted identifier (never the raw username/email) via `middleware/rateLimit.js`. The 50-per-15-min limit on login is measured against this repo's own test-suite volume (`classes.test.js` alone re-authenticates one seeded user 30 times in a single file), not guessed.
2. **Workflow approval TOCTOU race** — `workflowRepository.updatePendingStatus` (conditional `UPDATE ... WHERE status = 'Pending'`, the row lock itself is the concurrency guard) plus reordering `approveRequest`/`rejectRequest`/`escalateRequest` so the guarded update runs *before* `recordAction`/the audit log — a race loser now gets zero side effects, not just a bad state transition. Proven with a real two-connection concurrent test (deterministically forced via a controlled stale-read, since a naive `Promise.all` version was empirically shown to pass even against the unfixed code on a fast local Postgres).
3. **Background-job enqueue race** — `db/tenantTransaction.js` gained `registerAfterCommit`/an `AFTER_COMMIT_CALLBACKS` queue (Symbol-keyed on the request's AsyncLocalStorage context, kept out of the generic per-request log payload on purpose); `backgroundJobService.enqueue`'s worker trigger now fires only after the enqueuing transaction actually commits, never before.
4. **DB-level timeouts** — `ALTER ROLE arcnave_app SET lock_timeout='10s', statement_timeout='20s', idle_in_transaction_session_timeout='90s'` (migration `1762100000000`). Each value reasoned from real code shapes (generateTimetable's bounded statement loop; the 30s LLM adapter timeout and 60s OCR exec timeout the idle setting has to sit above), not a blind default.
5. **AI tool-invoke idempotency** — new `idempotency_keys` table (migration `1762200000000`, deliberately no status column — see its own comment for why atomicity makes one unnecessary) + `idempotencyKeyRepository.js` + `aiService.invokeToolIdempotent`, opt-in via an `Idempotency-Key` header on `POST /ai/tools/:name/invoke`. Reservation, business write, and completion all run on the same per-request transaction so a mid-request crash is safe either way (nothing committed, or the real response is already stored for replay). Caught and fixed a real bug during implementation: the reservation's unique-violation catch needed a `SAVEPOINT`/`ROLLBACK TO SAVEPOINT`, not a bare try/catch — Postgres aborts the whole transaction on any statement error, which broke the subsequent lookup.
6. **Security headers + CORS** — `helmet()` on both `tenantApp.js`/`platformApp.js`; `cors` (new dependency) scoped to one explicit `config.frontendOrigin` (default `http://localhost:3100`, the frontend's real dev port), never a wildcard — verified live via curl, not just unit tests.
7. **PDF/OCR pipeline protection** — fixed the accidental effective ~100KB upload cap (`express.json()`'s `req._body` short-circuit meant the route-level 15mb limit on `/documents/*` never actually applied; now a path-scoped parser ahead of the app-wide default); added a 60s exec timeout and a 250-page safety ceiling to `pdftoppm` (the page number is real evidence, not a guess — measured against the actual poppler build via `docker run gstack-app:latest`, a busy A4 page rasterized to ~650KB at 200 DPI; explicitly a technical safety net, not a product decision on real document size limits); added `ocr/ocrConcurrencyLimit.js`, a 2-slot in-process semaphore shared by both real OCR entry points (`documentExtractionService.runOcr` and `documentSearchService.js`'s ingestion, which previously had no shared choke point at all).

## Governing Principles Established This Session (apply these without re-deriving them)

- **Minimum sufficient work, scoped per-operation, not per-request.** A single-fact query may skip the LLM; a genuine multi-step request still needs planning + synthesis calls — never conflate the two.
- **"Less unnecessary work," not "less LLM calls."** A 4-tool workflow needing 2 reasoning calls (plan once, synthesize once) is correct; forcing it to 1 call or letting it balloon to 5+ are both wrong.
- **Verification is deterministic code, never a second LLM call.** Diff the LLM's numeric claim against the value already computed; correct in place.
- **GUI parity is bounded by Business Service coverage, not by what SQL could technically do.** There is no tool for "DROP TABLE" because there's no GUI button for it either — this is why AI can be capable without being an admin.
- **Interface/schema decisions get front-loaded pre-launch** (async contracts, worker abstractions, cache-hint slots); **usage-volume-gated infra decisions do not** (Redis, GPU, dedicated workers) — launch status doesn't change the latter.

## Local Dev Environment Notes

- Local Postgres via `docker compose up -d db` (container `gstack-db-1`), credentials in `backend/.env.local.sh` (source it before running tests/migrations). Docker Desktop itself is not always already running on this Windows environment — `docker info` fails silently if it isn't; start it and wait for `docker info` to succeed before `docker compose up`.
- Test command: `node --test "tests/**/*.test.js"` from `backend/` (the bare `node --test tests/` form fails on this Node version — use the glob).
- `node_modules` is not pre-installed in a fresh checkout of this environment — run `npm install` first (this also picks up `cors`, added in round 11 — a real, needed dependency, not a leftover).
- The backend's own Docker image (`gstack-app:latest`) already has `poppler-utils`/`pdftoppm` installed and is a fast way to get real (not mocked) measurements or behavior checks against the actual rasterization binary without installing poppler-utils on the host — `docker run --rm -v "D:/path/on/host:/work" gstack-app:latest sh -c "..."` (Windows-style `D:/...` path in the `-v` flag, not `/d/...`, or the bind mount silently fails to find the file).
